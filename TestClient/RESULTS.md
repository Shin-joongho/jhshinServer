측정일: 2026-09-08

## 환경

| | |
|---|---|
| CPU | Intel i5-13500 (물리 14 / 논리 20) |
| RAM | 64 GB |
| 빌드 | Release x64, MSVC v142, C++20 |
| 서버 설정 | 서비스 IOCP 워커 16, 리슨 1, AcceptEx 사전 게시 128 |

| 네트워크 | **루프백 (127.0.0.1)** — 클라이언트와 서버가 같은 머신 |

## 방법

`TestClient/LoadTest.cpp`

- 연결마다 스레드 1개. 전원 접속 완료 후 **배리어로 동시 출발** (순차 생성 시 계단식 부하가 되어 측정이 왜곡됨)
- 응답을 기다리지 않고 윈도우 W개를 미리 보낸 뒤, `응답 1개 수신 → 1개 추가 송신`으로 in-flight 유지
- 바디 앞 8바이트에 송신 시각을 심어 에코로 돌아온 값으로 왕복 지연 측정
- 클라이언트도 `TCP_NODELAY` 설정
- 측정 구간 10초

"왕복 1회" = 클라이언트 송신 1 + 서버 수신 1 + 서버 송신 1 + 클라이언트 수신 1.

| 4 | 159,863 | 0.199 | 0.246 | 0.297 |
| 16 | 219,710 | 0.453 | 1.524 | 2.787 |
| 50 | 214,230 | 0.473 | 2.357 | 8.601 |
| 100 | 219,716 | 0.447 | 2.391 | 13.439 |
| 200 | 267,882 | 5.583 | 8.114 | 9.070 |
| 500 | 260,734 | 14.676 | 16.315 | 22.197 |

500 연결까지 접속 실패·중간 끊김 0건.

**처리량은 16 연결 부근에서 이미 포화**되고 그 이상은 230k~270k 사이에서 평평하다. 지연은 연결 수에 비례해 증가한다 — 처리량이 고정된 상태에서 in-flight가 늘면 지연이 늘어나는 리틀의 법칙 그대로다. 500 연결 × 윈도우 8 = 4,000 in-flight를 260,000/초로 나누면 15.4 ms로, 실측 p50 14.7 ms와 일치한다.

## 2. 병목이 클라이언트인가 — in-flight 고정, 스레드 수만 변경

| 설정 | in-flight | 왕복/초 |
|---|---:|---:|
| 50 연결 × 윈도우 64 | 3,200 | 233,550 |
| 100 × 32 | 3,200 | 249,820 |
| 200 × 16 | 3,200 | 238,535 |
| 500 × 8 | 4,000 | 264,521 |

클라이언트 스레드 수를 10배 바꿔도 처리량이 평평하다. **클라이언트 스레드 오버헤드가 상한을 만든 것은 아니다.**

## 3. 병목의 성격 — 패킷 크기 변경 (200 연결 × 윈도우 16)

| 바디 | 왕복/초 | 단방향 MB/s |
|---:|---:|---:|
| 64 B | 237,461 | 15.4 |
| 256 B | 239,959 | 59.5 |
| 1,024 B | 253,707 | 248.7 |
| 2,048 B | 212,888 | 416.6 |

**바디를 32배 키워도 초당 왕복 수가 거의 변하지 않는다.** 처리량 상한이 바이트가 아니라 **패킷 개수**에 걸려 있다는 뜻이다. 대역폭(416 MB/s까지 선형 증가)은 한계가 아니다.

패킷당 약 4 µs가 소요되고 있으며, 후보는 다음과 같다.

1. **`ServiceManager::MakeSendPacket`의 전역 뮤텍스** — 모든 세션의 모든 송신이 `m_LastSendBuffer` 하나를 공유하므로 락 하나로 직렬화된다. 가장 유력하다.
2. 세션별 송신 큐 락 (`SessionData::m_SendLock`)
3. `WSARecv` / `WSASend` 시스템 콜 — 다만 송신은 이미 WSABUF 배열로 배칭되어 있다

1번이 맞다면 **SendBuffer 청크를 thread_local 또는 Room 단위로 소유**하도록 바꿨을 때 개선되어야 한다. 다음 측정 대상.

## 측정의 한계 — 이 수치로 주장할 수 없는 것

- **클라이언트와 서버가 같은 머신이다.** 클라이언트 스레드 200~500개가 서버 IOCP 워커 16개와 논리 프로세서 20개를 나눠 쓴다. 서버 단독 상한은 이보다 높을 수 있다.
- **루프백이라 실제 NIC·네트워크 스택 비용이 빠져 있다.**
- **꼬리 지연(p99·최대)은 서버 지연으로 해석할 수 없다.** 지연은 클라이언트 유저 공간에서 응답을 처리한 시점에 측정되므로, 200~500개 스레드가 20코어를 경합하며 생기는 **클라이언트 측 스케줄링 지연이 포함**되어 있다. 최대 10초는 그 오염으로 보는 편이 타당하다. p50까지는 신뢰할 만하다.

신뢰할 수 있는 결론은 두 가지다.

1. 이 환경에서 **초당 약 25만 왕복**이 상한이고 500 연결까지 안정적으로 유지된다.
2. 상한은 **대역폭이 아니라 패킷당 고정 비용**에서 온다.

## 6. 가설: 전역 SendBuffer 락 — 기각

`ServiceManager::MakeSendPacket`이 모든 세션의 모든 송신에 대해 `m_SendLock` 하나를 잡고 `m_LastSendBuffer`를 공유하는 구조였다. 이것이 직렬 구간이라고 보고, 청크를 `thread_local`로 옮겨 락을 제거했다.

청크 40,960 B ÷ 패킷 68 B ≈ 청크당 600 패킷이므로, 락 획득은 250,000/초 → 약 415/초로 줄어든다.

| 워커 | 변경 전 | 변경 후 | 차이 |
|---:|---:|---:|---:|
| 1 | 202,678 | 207,776 | +2.5% |
| 2 | 286,759 | 296,964 | +3.6% |
| 4 | 300,287 | 298,603 | −0.6% |
| 8 | 299,881 | 302,169 | +0.8% |
| 16 | 292,029 | 294,425 | +0.8% |

**전 구간 노이즈 범위(±3%). 가설 기각.** 전역 락은 병목이 아니었다.

변경 자체는 유지했다. 전역 락이 사라져 구조가 단순해지고, 이후 Room 단위 소유로 옮길 때 그대로 이어지기 때문이다. 다만 **이 환경에서 처리량 개선은 없었다.**

## 7. 가설: 클라이언트 프로세스 한계 — 기각

클라이언트가 왕복 1회당 시스템 콜을 3번(헤더 recv, 바디 recv, send) 부르므로 300k 왕복/초면 초당 90만 콜이다. 서버(왕복당 2회)보다 많아 클라이언트가 천장일 가능성을 검증했다.

| 구성 | 왕복/초 |
|---|---:|
| 클라 1개 × 200 연결 | 303,201 |
| 클라 2개 × 100 연결 | 155,820 + 156,003 = **311,823** |

프로세스를 둘로 나눠도 합계가 같다. **클라이언트 프로세스 단위의 한계가 아니다.**

## 결론

배제된 원인:

- 대역폭 — 패킷을 32배 키워도 왕복/초 불변 (3절)
- 클라이언트 스레드 수 — in-flight 고정 후 스레드 10배 변경해도 불변 (2절)
- 전역 SendBuffer 락 — 제거해도 불변 (6절)
- 클라이언트 프로세스 — 2개로 분산해도 합계 불변 (7절)

남는 설명은 **단일 머신 루프백에서 패킷당 커널 경로 비용**이다. 왕복 1회에 클라이언트 3 + 서버 2 = 시스템 콜 5회와 루프백 통과 2회가 발생하며, 300,000 왕복/초는 왕복당 약 3.3 µs에 해당한다.

즉 **이 측정에서 본 것은 서버의 한계가 아니라 측정 환경의 한계다.** 서버 자체 상한을 재려면 클라이언트를 별도 머신에 두고 실제 NIC를 거쳐야 한다.

# 8. CPU 귀속 — 병목 확정

서버에 모니터 스레드를 넣어 `GetProcessTimes`로 자기 CPU 사용량을 2초마다 출력하게 하고, 클라이언트에도 같은 계측을 추가했다.

**200 연결 × 윈도우 16 × 64 B, 302,050 왕복/초 구간:**

| 프로세스 | CPU | 비중 | 왕복/초/코어 |
|---|---:|---:|---:|
| 서버 (IOCP 워커 8) | 2.47 / 20 코어 | 12.3% | **122,300** |
| 클라이언트 (스레드 200) | 16.17 / 20 코어 | 80.8% | **18,700** |

합계 18.6 / 20 코어 = 머신의 93%로 사실상 포화. **그 부하의 대부분을 측정 도구가 만들고 있었다.**

서버는 코어 2.5개로 30만 왕복을 처리하며 17.5개를 놀리고 있다. **서버는 CPU 바운드가 아니라 대기 바운드다.** 앞서 6절에서 락을 제거해도 처리량이 변하지 않은 이유가 여기 있다 — 서버 내부의 어떤 최적화도 의미가 없는 상태였다.

## 효율 비교 — 같은 일에 6.5배

동일 머신, 동일 워크로드에서 코어당 처리량이 6.5배 차이난다.

- **서버**: IOCP 비동기 완료 모델, 워커 8개가 연결 200개를 담당
- **클라이언트**: 스레드-퍼-커넥션 블로킹 모델, 연결마다 스레드 1개

클라이언트는 패킷마다 블로킹 `recv`에서 깨어나며 컨텍스트 스위치가 발생하고, 왕복당 시스템 콜을 3회(헤더 recv, 바디 recv, send) 호출한다. 서버는 완료 통지를 워커 8개가 나눠 처리하고 송신은 WSABUF 배열로 배칭한다.

**IOCP를 쓰는 이유가 이 표에 그대로 나타난다.**

## 부수 확인

- `session 328/10000` — 접속 200 + AcceptEx 사전 게시 128. 20초 부하 내내 정확히 유지되어 **세션 누수 없음**을 확인했다. (Send 완료 실패 경로 수정이 유효)
- `chunk 13/1024` — 청크는 13~15개만 동시 사용된다. 1,024개는 과다하고 64개면 충분하다.

## 다음 단계

서버의 실제 상한을 재려면 클라이언트가 서버보다 가벼워야 한다. 둘 중 하나가 필요하다.

1. 클라이언트를 IOCP 또는 논블로킹 다중화로 재작성
2. 클라이언트를 별도 물리 머신에 두고 실제 NIC 경유

현재 수치는 **"서버가 12.3% CPU로 30만 왕복/초를 처리했다"**까지만 주장할 수 있고, 상한은 아직 보지 못했다.

# 9. 경량 클라이언트 — 서버의 실제 처리량

8절에서 병목이 측정 도구로 확인되어, 클라이언트를 다시 만들었다. (`TestClient/LoadTestFast.cpp`)

| | 기존 `LoadTest` | 경량 `LoadTestFast` |
|---|---|---|
| 동시성 모델 | 연결마다 스레드 1개 (블로킹) | 스레드 N개가 여러 연결을 논블로킹 + `WSAPoll` |

## 배칭이 지배적이다

윈도우 16 → 256으로 늘리면 처리량이 7.4배가 되는데 서버 CPU는 그대로다. 코어당 처리량이 316,579 → 2,077,420으로 **6.6배** 오른다.

윈도우가 커지면 한 번의 완료 통지에 여러 패킷이 함께 도착하고(`SessionData::Recv`의 `while( DivideBuffer() )` 루프가 여러 번 돈다), 송신도 큐에 쌓인 여러 패킷이 WSABUF 배열 하나로 나간다. **IOCP 완료와 시스템 콜 비용이 패킷 수로 나눠진다.**

서버의 `RecvBuffer`가 `PACKET_SIZE`(4,096 B)이므로 한 완료당 최대 약 60개(68 B 기준)까지 뭉칠 수 있다. 이 값이 배치 상한을 정하므로 다음 튜닝 후보다.

## 남은 한계

포화 지점에서도 서버 4.4 + 클라 3.5 = 약 8 / 20 코어로 **머신의 60%가 놀고 있다.** 즉 이 천장도 CPU가 아니다. 9.7M 왕복/초는 편도 582 MB/s, 양방향 약 1.3 GB/s로 루프백 데이터 경로 쪽 한계로 보인다.

또한 스레드 16개 설정에서 `GetProcessTimes` 값이 비현실적으로 낮게 나왔다(클라 0.29코어). Windows의 CPU 시간 계정이 타이머 틱 기반이라, 짧게 실행하고 자주 블로킹하는 스레드가 많아지면 과소 계상된다. **스레드 4~8 설정의 CPU 수치만 신뢰한다.**

여전히 단일 머신 · 루프백이고, 서버가 하는 일은 에코뿐이라 게임 로직 비용은 포함돼 있지 않다.

## 9절과 직접 비교하면 안 된다

**변수가 둘 바뀌었다.** 디스패치 도입과 바디 크기 변경(64 → 100 B)이 동시에 일어났다.

| | 왕복/초 | 편도 MB/s | 서버 CPU |
|---|---:|---:|---:|
| 9절 (직접 에코, 64 B) | 9,731,192 | 661 | 3.32 |
| 10절 (디스패치, 100 B) | 5,535,281 | 575 | 3.93 |

왕복 수는 43% 줄었지만 **바이트 처리량은 661 → 575 MB/s로 거의 같다.** 9절에서 확인한 데이터 경로 천장이 582 MB/s였으므로, 왕복 수 감소는 대부분 패킷이 68 → 104 B로 커진 결과다. 서버 CPU도 같은 범위(3.3~3.9 코어)에 머문다.

**디스패치로 인한 유의미한 비용은 관측되지 않았다.** 다만 정확한 수치는 이 데이터로 말할 수 없다 — 비교 실험은 한 번에 하나만 바꿔야 한다는 걸 놓쳤다.

## 남은 의심 — 핸들러의 중간 복사

```cpp
memcpy_s( &echoReq, sizeof( echoReq ), bufferData, bufferSize );   // 수신버퍼 -> echoReq
MakeSendPacket( ..., (char*)&echoReq, sizeof( echoReq ) );          // echoReq -> 청크
```

`MakeSendPacket`이 청크로 복사하므로 앞의 복사는 순수 추가 비용이다. 초당 550만 패킷 × 100 B = **약 550 MB/s의 여분 memcpy**이며, 바이트 처리량 13% 차이의 유력한 원인이다.

실제 게임 패킷은 구조체로 역직렬화해 필드를 읽어야 하므로 이 패턴이 맞지만, 에코는 받은 버퍼를 그대로 넘기면 된다. 다음 측정 대상.

# 11. 디스패치 비용 재측정 — 변수를 분리하다

10절에서 왕복 수가 43% 줄어 보였으나, 디스패치 도입과 바디 크기 변경(64 → 100 B)이 동시에 일어나 원인을 가릴 수 없었다. 두 가지를 되돌려 **변수를 하나만 남겼다.**

- `Client_ECHO_Req`를 64 B로 되돌림 → 9절과 동일한 68 B 패킷
- 에코 핸들러의 중간 복사 제거 → `bufferData`를 `MakeSendPacket`에 직접 전달

이제 9절과의 유일한 차이는 **패킷 디스패치 경유 여부**다.

## 윈도우 스윕 (200 연결, 스레드 8, 바디 64 B)

| 윈도우 | 9절 (직접 에코) | 11절 (디스패치) | 차이 |
|---:|---:|---:|---:|
| 16 | 1,206,166 | 1,208,673 | +0.2% |
| 32 | 2,358,542 | 2,370,540 | +0.5% |
| 64 | 4,469,457 | 4,555,837 | +1.9% |
| 128 | 7,670,962 | 7,569,362 | −1.3% |
| 256 | 8,974,453 | 8,760,121 | −2.4% |
| 512 | 8,957,330 | 8,543,162 | −4.6% |

윈도우 128·256은 3회 측정 중앙값. 나머지는 단일 측정.

## 최고 기록 비교

| | 9절 | 11절 (3회 중앙값) | 차이 |
|---|---:|---:|---:|
| 100 연결 × 창 256 × 스레드 4 | 9,731,192 | 9,401,478 | −3.4% |
| 서버 CPU | 3.32 | 4.05 | — |

서버 CPU는 측정 간 변동이 커서(같은 설정에서 3.3~5.3 코어) 이 정밀도로는 비교가 어렵다. 스윕 전체의 중앙값으로 보면 9절 약 4.0, 11절 약 3.85로 사실상 동일하다.

## 결론

**디스패치 도입 비용은 측정 오차 이하다.** 처리량 차이가 −4.6% ~ +1.9%로, 앞서 확인한 반복 변동폭(±3~12%) 안에 들어간다.

배열 인덱싱 1회와 함수 포인터 간접 호출 1회는 패킷당 수 나노초 수준이므로 예상과 일치한다.

**10절에서 관측된 26% 효율 저하는 디스패치가 아니라 다음 둘 때문이었다.**

1. **패킷이 68 → 104 B로 커짐 (1.53배)** — 데이터 경로 천장(약 580 MiB/s)에 걸린 상태였으므로 패킷이 커진 만큼 왕복 수가 줄었다. 9,401,478 ÷ 1.53 = 6.14M 으로, 10절 실측 5.5M과 대체로 일치한다.
2. 핸들러가 수신 버퍼를 `Client_ECHO_Req`에 복사한 뒤 그것을 다시 청크로 복사 — 여분의 memcpy

둘을 되돌리자 9절 수준으로 복귀했다.

**다만 2번의 기여는 거의 없었다.** 12절에서 `memcpy` 비용을 따로 측정한 결과, 100 B 복사는 약 1 ns이므로 초당 550만 회여도 코어 하나의 0.55% 수준이다. **1번이 사실상 전부였다.**

처음에는 "여분 memcpy가 초당 550 MB"라는 크기에 눈이 갔지만, 절대 시간으로 환산해 보기 전에는 그 숫자가 큰지 작은지 알 수 없었다.

## 배운 것

비교 실험에서 변수를 둘 이상 동시에 바꾸면 **결과를 해석할 수 없다.** 10절은 "디스패치 비용이 관측되지 않았다"는 잘못된 결론으로 이어질 뻔했고, 실제로는 반대 방향(26% 저하)의 수치를 보고 있었다. 변수를 하나씩 되돌려 재측정한 뒤에야 두 원인이 분리되었다.

측정 도구를 만들 때(9절)도, 측정 조건을 바꿀 때(11절)도 같은 실수를 반복했다는 점을 기록해 둔다.

# 12. `memcpy` vs `memcpy_s` 마이크로벤치마크

11절에서 "여분 memcpy"를 원인 후보로 지목했으므로, 실제 비용을 따로 쟀다.

## 조건

MSVC v142, Release `/O2`, x64. 3천만 회 반복. 64개 슬롯을 순환해 L1에 상주하는 최선 조건이며, 최적화 제거를 막기 위해 매 회 목적지 첫 바이트를 체크섬에 더한다.

## 결과 (호출당 평균)

| 크기 | `memcpy` | `memcpy_s` | 배수 | 절대 차이 |
|---:|---:|---:|---:|---:|
| 64 B | 0.60 ns | 0.78 ns | 1.30× | +0.18 ns |
| 128 B | 1.13 ns | 1.17 ns | 1.04× | +0.04 ns |
| 256 B | 2.24 ns | 2.26 ns | 1.01× | +0.02 ns |
| 1,024 B | 16.95 ns | 17.93 ns | 1.06× | +0.98 ns |
| 4,096 B | 68.86 ns | 69.72 ns | 1.01× | +0.86 ns |

`memcpy_s`의 추가 비용은 **호출당 0.2 ns 안팎의 고정값**이다. 64 B에서 30%로 보이는 것은 분모가 작기 때문이다.

초당 940만 패킷 기준으로 환산하면 9.4M × 0.18 ns = 1.7 ms/초, 즉 **코어 하나의 0.17%**다. 측정 가능한 수준이 아니다.

## 그래서 `memcpy_s`를 서버에 쓸 것인가

속도는 판단 근거가 못 된다. 실제로 고려할 것은 의미론이다.

**① 제약 위반 시 기본 동작이 프로세스 종료다.** MSVC의 `_s` 계열은 invalid parameter handler를 호출하고, 기본 핸들러는 프로세스를 끝낸다. 잘못된 패킷 하나로 서버 전체가 내려갈 수 있다. 사용한다면 `_set_invalid_parameter_handler`로 로깅 후 계속 진행하도록 바꿔야 한다.

**② 실패 시 목적지를 0으로 채운다.** MSVC 구현은 `destSize < count`이면 `memset( dst, 0, destSize )`를 먼저 실행한다. 부분 복사가 아니라 대상 버퍼 파괴다.

**③ 막아주는 것은 목적지뿐이다.** 소스 버퍼의 크기는 알지 못하므로, 네트워크 코드에서 정작 위험한 "수신 버퍼에 그만큼의 데이터가 실제로 있는가"는 보장하지 못한다. 그것은 `RecvBuffer::DivideBuffer`가 책임지는 영역이다.

**④ Annex K는 C11의 선택적 부록**이라 glibc는 구현하지 않는다. Linux 포팅 시 전부 걷어내야 한다.

**결론.** 크기를 이미 명시적으로 검증했다면 `memcpy`로 충분하다. 검증하지 않았다면 `memcpy_s`에 맡기는 대신 `if`로 직접 검사하는 편이 낫다 — 실패 시 동작(세션 종료 / 무시 / 로깅)을 직접 정할 수 있고 의도가 코드에 드러난다.

현재 에코 핸들러는 `if( bufferSize != sizeof( echoReq ) ) return false;`로 이미 검증하고 수신 버퍼를 그대로 `MakeSendPacket`에 넘긴다.
