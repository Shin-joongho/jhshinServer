# jhshin_Server

**Windows IOCP 기반 C++ 게임 서버 — 네트워크 계층 · 룸 · 이동 동기화**

외부 네트워크 라이브러리 없이 **Winsock2 / IOCP**로 네트워크 계층을 직접 구현하고, 룸 단위 JobQueue로 **공유 락 없이** 게임 상태를 처리합니다.
구현마다 테스트와 부하 측정으로 설계의 장단점을 확인했고, 그 과정을 [`RESULTS.md`](TestClient/RESULTS.md)의 15개 절에 남겼습니다.

---

## 핵심 결과

- **좌표 갱신 120만 건을 SendBuffer 청크 5 / 1024개로 전달했습니다.**
  틱마다 룸당 스냅샷을 하나만 만들어 인원이 공유하므로, 인원이 늘어도 만드는 패킷 수는 그대로입니다. → [3-6](#3-6-이동-동기화)
- **이동 도착 좌표 오차 0, 룸 간 누출 0건입니다.**
  위치를 저장하지 않고 시간으로 계산해, 틱이 밀려도 좌표가 틀어지지 않습니다. → [5절](#5-검증)
- **병목은 서버가 아니라 부하 클라이언트였습니다.**
  CPU를 프로세스별로 나눠 재고 클라이언트를 다시 만들자 측정 처리량이 32배로 올랐고, 서버 CPU는 1.3배였습니다. → [6절](#6-부하-측정과-병목-분석)
- **테스트가 버그 두 개를 찾았습니다.**
  끊긴 세션이 재사용된 소켓 번호로 남의 연결에 송신하던 문제, `NaN` 좌표가 경계 검사를 통과해 영구 오염되던 문제입니다. → [5절](#5-검증)

  │

# 2. 전체 구조

```text
main
├─ ServiceManager
│  ├─ IOCP              워커 풀 / 완료 라우팅
│  ├─ SendBuffer 풀     40KB 청크
│  └─ 세션 맵
│
├─ ListenManager        리슨 소켓 · AcceptEx 사전 게시
│
├─ SessionManager
│  └─ 세션 풀 + Accept 대기 큐
│      └─ SessionData   소켓 · RecvBuffer · 송신 큐
│           ├─ RecvObject (OVERLAPPED)
│           └─ SendObject (OVERLAPPED)
│
└─ RoomManager
   └─ Room × N          룸마다 전용 스레드 1개
       ├─ JobQueue      Enter · Leave · Broadcast · Move
       └─ 100 ms 틱     이동 중인 인원의 좌표 스냅샷 전송
```

룸 상태 변경 요청은 IOCP 워커가 직접 처리하지 않고 해당 룸의 `JobQueue`로 전달합니다.
하나의 룸 상태는 그 룸의 스레드만 접근하므로 `Room` 안에 공유 락이 없습니다.

# 3. 핵심 설계

## 3-1. TCP 패킷 경계 복원

TCP는 메시지 경계를 보장하지 않으므로 IOCP 완료 통지 1회가 패킷 1개를 뜻하지 않습니다.

한 번의 수신에서 패킷이 쪼개지거나 여러 개가 합쳐질 수 있어, `RecvBuffer`에 누적한 뒤 헤더의 크기를 기준으로 **완성된 패킷만 소비**합니다.

```cpp
int divideByte = transferByte;
RecvBuffer& recvBuffer = m_Recv.GetRecvBuffer();

while (recvBuffer.DivideBuffer(divideByte))
{
    divideByte = 0;

    const int size = recvBuffer.GetPacketID()._size + PacketID_SIZE;

    // packet processing

    recvBuffer.SetReadPos(size);
}
```

클라이언트가 비정상적으로 큰 크기를 보내 버퍼를 영구 점유하지 못하도록 **패킷 크기 상한**도 검사합니다.

---

## 3-2. 세션 수명 관리

IOCP에 `WSARecv` / `WSASend`를 게시하면 커널이 `OVERLAPPED`와 버퍼 주소를 계속 참조합니다.
세션을 풀로 즉시 반납하면 늦게 도착한 완료 통지가 재사용된 세션을 잘못 참조할 수 있습니다.

그래서 세션을 `shared_ptr` 참조 계수로 관리하고, 마지막 참조가 풀릴 때 custom deleter가 **세션 풀로 반환**합니다.

```cpp
return SessionDataRef(
    session,
    [](SessionData* p)
    {
        SessionManager::This()->PushSession(p);
    }
);
```

`shared_ptr`는 여기서 메모리 관리 도구가 아니라 **세션 재사용 시점을 제어하는 장벽**입니다.
`RecvObject`와 `SendObject`가 각각 세션을 참조하므로, 비동기 작업이 남아 있는 동안에는 세션이 재사용되지 않습니다.

```text
게시 중인 IO  → reference +1
세션 맵       → reference +1

모든 참조 해제
      ↓
reference = 0
      ↓
custom deleter
      ↓
session pool 반환
```

## 3-3. 송신 직렬화와 배칭

한 세션에는 동시에 하나의 `WSASend`만 게시합니다.
송신 요청은 먼저 큐에 넣고, 게시 중인 송신이 없을 때만 새 `WSASend`를 시작합니다.

송신이 끝나면 남은 큐를 이어서 보내고, 부하가 높을수록 큐에 쌓인 여러 패킷이 하나의 `WSABUF` 배열로 묶입니다.
별도의 배칭 로직을 두지 않고 **직렬화 구조에서 배칭이 자연스럽게 생기도록** 했습니다.

```text
Send Request
     │
     ▼
 Send Queue
     │
     ├─ Send 진행 중 → Queue에 저장
     │
     └─ Send 없음 → WSASend 게시
                      │
                      ▼
                  완료 통지
                      │
                      ▼
                  다음 Send
```

## 3-4. SendBuffer 공유

브로드캐스트는 같은 데이터를 여러 세션에 보냅니다.
직렬화한 데이터를 40KB `SendBuffer` 청크에 한 번만 담고, 여러 세션이 같은 `SendChunk`를 참조합니다.

```cpp
struct SendChunk
{
    SendBufferRef m_sendBuffer;
    char*         m_buffer;
    int           m_size;
};
```

```text
직렬화 / 복사
      ↓
     1회
      ↓
같은 SendChunk를 N개 세션이 공유
```

복사는 한 번이고 공유는 N번입니다. 메모리 수명은 참조 계수가 관리합니다.

## 3-5. 룸 단위 JobQueue

여러 IOCP 워커가 룸 상태를 직접 바꾸면 `Room` 안에 공유 락이 필요합니다.
브로드캐스트는 인원에 비례하는 O(N) 작업이라, 룸 전체를 락 하나로 보호하면 경합이 커진다고 판단했습니다.

대신 **룸마다 전용 스레드를 두고**, 워커는 상태 변경 요청을 그 룸의 `JobQueue`에 넣기만 합니다.

```text
IOCP Worker
    │
    ├─ ENTER
    ├─ LEAVE
    ├─ BROADCAST
    └─ MOVE
          │
          ▼
       JobQueue
          │
          ▼
      Room Thread
          │
          ▼
       Room State
```

- 룸 상태는 룸 스레드만 소유하므로 `Room` 안에 mutex가 없습니다
- 같은 룸의 작업은 들어온 순서대로 처리됩니다
- `JobQueue::PopAll()`은 `swap`으로 작업 목록을 통째로 가져와 락 획득을 배치 단위로 줄입니다

대가는 **룸 하나의 처리량이 스레드 하나로 제한된다**는 것입니다. 이 제약이 지연으로 드러나는 조건은 아직 특정하지 못했으며, 측정과 재현 시도는 [6절](#6-부하-측정과-병목-분석)과 [`RESULTS.md` 14절](TestClient/RESULTS.md)에 남겼습니다.

## 3-6. 이동 동기화

룸 위에 좌표를 올리면서 **위치를 저장하지 않고 계산하는 방식**을 택했습니다.

`RoomUser`가 들고 있는 것은 현재 좌표가 아니라 **출발 좌표 · 출발 시각 · 목적지 · 도착 예정 시각**입니다. 현재 위치는 필요한 순간에 경과 시간 비율로 구합니다.

```cpp
비율 = ( 지금 - 출발 시각 ) / ( 도착 시각 - 출발 시각 )
x    = 출발X + ( 목적지X - 출발X ) * 비율
```

**틱이 밀려도 위치가 틀어지지 않습니다.** 틱마다 조금씩 더하는 방식이면 간격이 흔들릴 때마다 오차가 쌓이지만, 시간으로 계산하면 틱은 "언제 알려줄지"만 정하고 "어디에 있는지"는 시간이 정합니다.

대신 규칙이 하나 생깁니다. **위치를 읽기 전에는 항상 `MovePosition`을 먼저 부릅니다.** 이동 요청, 틱, 스폰 전송이 모두 이 함수를 지나므로 이동 중 상태가 어긋나지 않습니다.

### 전파는 이벤트가 아니라 주기 스냅샷

목적지가 바뀔 때마다 보내는 대신, **룸 스레드가 100 ms마다 이동 중인 인원의 좌표를 묶어서** 보냅니다.

```text
룸 스레드
  │
  ├─ 잡 처리 (Enter / Leave / Move / Broadcast)
  │
  └─ 100 ms 경과 시
        │
        ├─ 이동 중인 인원만 위치 계산
        ├─ 좌표를 한 패킷으로 묶음 (최대 100명)
        └─ MakeSendPacket 1회 → 청크를 룸 인원이 공유
```

- **전파량이 정해집니다.** 이벤트 기반이면 전파량이 이용자 행동에 좌우되어 시야 처리 전후를 비교하기 어렵습니다. 주기 전파에서는 `인원 × 시야 안 인원 × 틱레이트`로 고정됩니다
- **멈춘 이용자는 트래픽을 만들지 않습니다.** 스냅샷에는 이동 중인 인원만 담깁니다
- **틱을 위해 `JobQueue::PopAll`의 대기를 `wait_for`로 바꿨습니다.** 잡이 오거나 주기가 지나면 깨어나므로 패킷이 없어도 좌표가 전파됩니다. 대신 유휴 상태에서도 100 ms마다 깨어나므로, 이 절 이후의 측정은 앞선 측정과 유휴 CPU 기준이 다릅니다

### 오브젝트 ID

룸이 `seqID` 풀을 큐로 들고 입장 시 발급, 퇴장 시 반납합니다. 룸 스레드만 발급하므로 `atomic`이 필요 없습니다.

반납은 **퇴장 통지를 실제로 보낸 경우에만** 합니다. 통지에 실패한 번호를 반납하면, 남은 이용자가 사라진 엔티티를 든 채로 그 번호가 재사용될 수 있습니다. 반납하지 않으면 정원이 하나 줄지만 그쪽은 모니터에 보이는 손실입니다.

# 4. 추가 설계 판단

| 항목 | 선택 | 이유 |
|---|---|---|
| RecvBuffer | 선형 버퍼 + compaction | 파싱에 연속 메모리가 필요해, 버퍼 끝을 넘는 패킷을 다시 조립해야 하는 링 버퍼보다 단순한 구조를 우선 |
| 세션 풀 저장소 | `unique_ptr<T[]>` | `SessionData`가 mutex를 가져 `vector<T>` 재할당 제약을 피하고, 꺼낸 객체의 주소가 바뀌지 않게 함 |
| Accept 대기 큐 | 세션 고갈 시 보관 후 재게시 | 풀이 비어도 `AcceptEx` 요청을 버리지 않음 |
| AcceptEx 주소 파싱 | 런타임 함수 포인터 취득 | `WSAIoctl(SIO_GET_EXTENSION_FUNCTION_POINTER, ...)` |

| 같은 룸 관찰자 | 이동자와 같은 스냅샷 수신 |
| 다른 룸 누출 | **0건** |
| 경계 밖 · 제자리 · `NaN` 요청 | 거부 |
| 퇴장 통지 | 정상 |

소요 시간이 0.11초 긴 것은 **스냅샷이 100 ms 틱이라 도착 통지가 최대 1틱 늦기 때문**입니다. 좌표 오차가 0인 채 시각만 밀린 것이 그 근거입니다.

### 테스트가 찾은 버그

**재사용된 소켓 번호로 남의 연결에 송신** — 전달률이 100%를 넘는 이상치를 추적해 찾았습니다. 끊긴 세션이 룸에 남은 채 Windows가 같은 소켓 번호를 새 연결에 주면, 죽은 세션의 송신이 무관한 연결로 나갔습니다. 모든 종료 경로가 룸 퇴장을 거치도록 고쳤습니다. ([`RESULTS.md` 13절](TestClient/RESULTS.md))

**`NaN` 좌표의 영구 오염** — 경계 검사를 부등호로만 했더니 `NaN`이 그대로 통과했습니다. `NaN`은 모든 비교에서 거짓이기 때문입니다. `NaN`은 같은 룸 전원에게 전파되고, 이후 정상 좌표로도 복구되지 않으며, 도착 판정이 서지 않아 100 ms마다 스냅샷이 계속 나갔습니다. 경계 검사 앞에 `isfinite` 검사를 넣어 막았습니다. ([`RESULTS.md` 15절](TestClient/RESULTS.md))

두 번째 버그의 교훈은 한 줄입니다. 이 서버는 **패킷 크기는 검증하면서 값은 검증하지 않고 있었습니다.**

# 6. 부하 측정과 병목 분석

최고 수치를 뽑기보다 **병목 가설을 세우고 측정으로 검증하거나 기각**했습니다. 모든 측정은 Release x64 · C++20 · 루프백입니다.

| | ECHO 스윕 | 룸 / 브로드캐스트 | 이동 동기화 |
|---|---|---|---|
| 논리 프로세서 | 20 (i5-13500) | 6 | 20 (i5-13500) |
| 툴체인 | MSVC v143 | MSVC v143 | MSVC v142 |

**머신이 다른 측정끼리는 숫자를 직접 비교하지 않습니다.**

### 주요 결과

| 경로 | 구성 | 결과 |
|---|---|---|
| ECHO | 연결 50 | 왕복 **661,169 /초** · p50 0.499 ms |
| Broadcast | 룸 다수 · 팬아웃 약 9 | 유출 약 **104,000 /초**까지 전달률 100% · p50 1.07 ms |

### 이동 동기화 — 300 연결

`MoveTest.exe swarm 300 12`. 각 연결은 목적지에 도착하면 0.5~1.5초 쉬었다가 다음 목적지를 고릅니다.

| 항목 | 값 |
|---|---:|
| 동시 연결 | 300 (룸 5개, 48~69명) |
| 이동 요청 | 1,437 건 |
| 전달된 좌표 갱신 | **1,205,301 건** (12초) |
| 서버 CPU | 0.02 / 20 코어 |
| SendBuffer 청크 사용 | **5 / 1024** |
| 0.35초 초과 정지 | 1,136 회 (평균 1.00초) |

**청크가 5개에 머문 것은 설계의 결과입니다.** 틱 한 번에 룸당 `MakeSendPacket`은 1회이고, 인원에 비례해 늘어나는 것은 송신 큐에 들어가는 참조뿐입니다. 루프 안에서 만들었다면 초당 3,000개를 소모해 1,024개 풀이 1초를 버티지 못합니다.

이동 요청 한 건은 평균 **839건**의 좌표 갱신으로 퍼졌습니다. 이 배수는 `이동에 걸친 틱 수 × 룸 인원`이고, **뒤쪽 항이 시야 처리를 넣었을 때 줄어드는 자리**입니다. 같은 명령으로 전후를 재면 그대로 비교가 됩니다.

서버 CPU 0.02 코어는 **부하가 서버에 닿지 않았다**는 뜻입니다. 이 측정은 전파 구조의 비용을 보여줄 뿐 서버의 상한이 아닙니다.

### 측정 도구가 병목이었다

연결당 스레드 방식의 부하 클라이언트로 재던 중, 서버와 클라이언트의 CPU를 따로 재 보니 **머신 CPU의 80%를 클라이언트가 쓰고 서버는 12%를 쓰고 있었습니다.** 서버는 처음부터 병목이 아니었습니다.

클라이언트를 논블로킹 + 배칭 구조로 다시 만들자 같은 머신에서 측정 처리량이 **32배**가 되었고, 그동안 서버 CPU는 1.3배만 늘었습니다. ([`RESULTS.md` 8~9절](TestClient/RESULTS.md))

### 기각한 가설

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 전역 SendBuffer 락 | `thread_local` 적용 후 재측정 | 처리량 불변 → 기각 |
| 클라이언트 프로세스 한계 | 부하 클라이언트 2프로세스 분할 | 총량 불변 → 기각 |
| 대역폭 | 패킷 바디 32배 확대 | 왕복/초 불변 → 기각 |

### 팬아웃과 지연 — 조건을 특정하지 못함

논리 6코어에서, 유출량이 비슷해도 **룸 크기에 따라 지연이 크게 갈리는** 구간을 관측했습니다.

| 구성 | 팬아웃 | 유출/초 | p50 |
|---|---:|---:|---:|
| 연결 50 × rate 200 | 약 11 | 120,994 | 0.37 ms |
| 연결 100 × rate 50 | 약 24 | 121,676 | **244 ms** |

`Room::BroadCast`가 룸 멤버를 한 스레드에서 동기로 순회하므로 룸이 클수록 뒤쪽 멤버가 밀린다고 해석했습니다.

그러나 이후 **논리 20코어에서 같은 비교를 다시 돌렸을 때는 격차가 나타나지 않았습니다** — 팬아웃 10과 20에서 p50이 0.244 ms와 0.253 ms로 사실상 같았고, affinity로 6코어에 묶어도 마찬가지였습니다. 머신·툴체인·코드가 동시에 바뀌어 **원인을 분리하지 못했습니다.** 재현 시도와 분리하지 못한 변수는 [`RESULTS.md` 14절](TestClient/RESULTS.md)에 남겼습니다.

`Room::BroadCast`가 한 스레드에서 동기로 순회한다는 **구조적 사실은 그대로**입니다.

> 모든 측정의 상세 과정은 [`TestClient/RESULTS.md`](TestClient/RESULTS.md)의 15개 절에 있습니다.

# 9. 빌드 및 실행

Visual Studio 2022에서 `jhshin_Server/jhshin_Server.sln`을 x64로 빌드합니다. 기본 포트는 `27130`입니다.

### 테스트 클라이언트

**x64 Native Tools Command Prompt**에서 빌드합니다.

```bat
cl /nologo /utf-8 /wd4819 /std:c++20 /O2 /EHsc ^
   /I jhshin_Server\jhshin_Server ^
   TestClient\LoadTestRoom.cpp ^
   /Fe:LoadTestRoom.exe ws2_32.lib

cl /nologo /utf-8 /wd4819 /std:c++20 /O2 /EHsc ^
   /I jhshin_Server\jhshin_Server ^
   TestClient\MoveTest.cpp ^
   /Fe:MoveTest.exe ws2_32.lib
```

소스는 모두 UTF-8(BOM)입니다. `/wd4819`는 한글이 포함된 소스에서 시스템 코드 페이지에 따라 뜨는 경고를 끄기 위한 것이며, 파일 인코딩 문제는 아닙니다. 서버 솔루션 빌드는 경고 없이 통과합니다.

```bat
LoadTestRoom.exe verify
LoadTestRoom.exe load [연결수] [지속초] [초당송신/연결] [스레드수]

MoveTest.exe                 검증 14항목
MoveTest.exe swarm 300 12    300 연결 군집 이동
```
