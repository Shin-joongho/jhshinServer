# jhshin_Server

**Windows IOCP 기반 C++ 게임 서버 네트워크 계층 프로젝트**

TCP 스트림에서 패킷 경계를 복원하고, 다중 워커 스레드 환경에서 세션 수명을 안전하게 관리하며, **룸 단위 JobQueue를 통해 공유 락 없이 게임 상태를 처리하는 구조**를 직접 구현했습니다.

외부 네트워크 라이브러리 없이 **Winsock2 / MS IOCP를 직접 사용**했으며, 구현 과정에서 발생한 설계 선택과 성능 측정 결과를 함께 기록했습니다.

> **핵심 키워드**  
> C++20 · Windows IOCP · Winsock2 · 멀티스레드 · JobQueue · Session Pool · Object Pool · Broadcast · 성능 측정

| 측정 | 결과 |
|---|---|
| ECHO | 왕복 **661,169 /초** · p50 0.499 ms (논리 6코어) |
| Broadcast | 유출 **약 104,000 msg/초**까지 전달률 100% · p50 1.07 ms (논리 6코어) |
| 재측정 | 논리 20코어에서 유출 **약 100,000 /초** 100% 전달 · p50 0.25 ms |

루프백 기준. 측정 조건과 기각한 가설은 [6. 부하 측정](#6-부하-측정)에 정리했습니다.

이전 측정 중 **재현되지 않은 결과가 하나 있고, 원인을 특정하지 못한 상태 그대로** [`RESULTS.md` 14절](TestClient/RESULTS.md)에 남겼습니다.

## 이 프로젝트에서 고민한 것

이 프로젝트는 단순히 IOCP를 사용하는 것보다,

> **"어디에 락을 걸 것인가?"보다 "누가 데이터를 소유하고 언제 재사용할 수 있는가?"**

에 초점을 맞춰 설계했습니다.

세션 수명은 참조 계수가, 룸 상태는 단일 스레드 소유권이, 송신 순서는 직렬화 구조가 각각 보장하도록 만들었고, 그 판단이 실제로 맞았는지를 부하 측정으로 확인했습니다. 측정 과정에서 세운 가설 중 일부는 기각됐고, 그 기록도 함께 남겼습니다.

## 2. 전체 구조

```text
main
├─ ServiceManager
│   ├─ IOCP            워커 풀 / 완료 라우팅
│   ├─ SendBuffer 풀   40KB 청크
│   └─ 세션 맵
│
├─ ListenManager       리슨 소켓 · AcceptEx 사전 게시 · 확장 함수 포인터
│
├─ SessionManager
│   └─ 세션 풀 + Accept 대기 큐
│        └─ SessionData   소켓 · RecvBuffer · 송신 큐
│             ├─ RecvObject (OVERLAPPED)
│             └─ SendObject (OVERLAPPED)
│
└─ RoomManager
    └─ Room × N        룸마다 전용 스레드 1개
         └─ JobQueue
              ├─ Enter
              ├─ Leave
              └─ Broadcast
```

### 실행 모델

```text
[IOCP Worker]
      │
      │ 네트워크 이벤트
      ▼
[PacketHandler]
      │
      ├─ 일반 요청 → 즉시 처리
      │
      └─ 룸 상태 요청
             │
             ▼
        [JobQueue]
             │
             ▼
        [Room Thread]
             │
             └─ Room 상태 변경
```

IOCP 워커는 네트워크 이벤트를 처리하고, **룸 상태를 변경하는 작업은 해당 룸의 JobQueue로 전달**합니다.

따라서 하나의 룸 상태는 해당 룸의 스레드만 접근하며, `Room` 내부에 별도의 공유 락을 두지 않습니다.

## 3. 핵심 설계

### 3-1. TCP 패킷 경계 복원

TCP는 메시지 경계를 보장하지 않기 때문에 `recv` 또는 IOCP 완료 통지 1회가 패킷 1개를 의미하지 않습니다.

하나의 수신에

- 패킷이 일부만 도착하거나
- 여러 패킷이 한 번에 도착하거나
- 한 패킷이 여러 번에 걸쳐 도착할 수 있습니다.

이를 처리하기 위해 `RecvBuffer`에 수신 데이터를 누적하고, 헤더의 크기를 기준으로 **완성된 패킷만 소비하는 방식**으로 구현했습니다.

```cpp
int divideByte = transferByte;
RecvBuffer& recvBuffer = m_Recv.GetRecvBuffer();

while (recvBuffer.DivideBuffer(divideByte))
{
    divideByte = 0;

    const int size = recvBuffer.GetPacketID()._size + PacketID_SIZE;

    // packet processing

    recvBuffer.SetReadPos(size);
}
```

또한 클라이언트가 비정상적으로 큰 패킷 크기를 전달했을 때 버퍼가 영구적으로 점유되지 않도록 **패킷 크기 상한 검증**을 적용했습니다.

### 3-2. 세션 수명 관리

IOCP에 `WSARecv` / `WSASend`를 게시하면 커널이 `OVERLAPPED`와 버퍼 주소를 계속 참조합니다.

세션을 풀로 반납한 직후 해당 메모리가 다른 연결에 재사용되면, 늦게 도착한 완료 통지가 **새 연결을 잘못 참조하는 문제**가 발생할 수 있습니다.

이를 해결하기 위해 세션은 `shared_ptr` 기반 참조 계수로 관리하고, custom deleter를 통해 마지막 참조가 해제될 때 실제 메모리를 삭제하는 대신 **세션 풀로 반환**하도록 구성했습니다.

```cpp
return SessionDataRef(
    session,
    [](SessionData* p)
    {
        SessionManager::This()->PushSession(p);
    }
);
```

즉 `shared_ptr`은 여기서 단순한 메모리 관리 도구가 아니라 **세션 재사용 시점을 제어하는 장벽**으로 사용됩니다.

```text
게시 중인 IO  → reference +1
세션 맵       → reference +1

모든 참조 해제
       ↓
reference = 0
       ↓
custom deleter
       ↓
session pool 반환
```

`RecvObject` / `SendObject`가 세션을 각각 참조하므로 둘 중 하나의 비동기 작업이 아직 완료되지 않았다면 세션이 재사용되지 않습니다.

### 3-3. 송신 직렬화와 배칭

하나의 세션에는 동시에 하나의 `WSASend`만 게시하도록 구성했습니다.

송신 요청은 큐에 먼저 넣고, **게시 중인 송신이 없을 때만 새로운 `WSASend`를 시작**합니다.

```text
Send Request
     │
     ▼
[Send Queue]
     │
     ├─ Send 진행 중 → Queue에 저장
     │
     └─ Send 없음 → WSASend 게시
                       │
                       ▼
                 완료 통지
                       │
                       ▼
                  다음 Send
```

송신 완료 시 남은 데이터를 확인해 다음 전송을 이어가며, 부하가 높을수록 큐에 쌓인 여러 패킷이 하나의 `WSABUF` 배열로 묶이는 구조입니다.

즉 별도의 복잡한 batching 로직을 추가하기보다 **송신 직렬화 구조 자체에서 자연스럽게 배칭이 발생하도록 설계**했습니다.

### 3-4. SendBuffer 공유

브로드캐스트에서는 동일한 패킷을 여러 세션으로 보내야 합니다.

이를 위해 직렬화된 데이터를 40KB `SendBuffer` 청크에 저장하고, 여러 세션은 같은 `SendChunk`를 참조하도록 구성했습니다.

```cpp
struct SendChunk
{
    SendBufferRef m_sendBuffer;
    char* m_buffer;
    int m_size;
};
```

따라서 N명의 세션에 같은 데이터를 전송할 때

```text
직렬화 / 복사
       ↓
    1회 수행
       ↓
같은 SendChunk를 N개 세션이 공유
```

하는 구조가 됩니다.

브로드캐스트에서 패킷 데이터 자체를 여러 번 복사하는 비용을 줄이고, 실제 메모리 수명은 참조 계수로 관리합니다.

### 3-5. 룸 단위 JobQueue

룸의 상태를 여러 IOCP 워커가 직접 변경하면 `Room` 내부에 공유 락이 필요합니다.

하지만 브로드캐스트는 룸 인원 수에 비례하는 O(N) 작업이기 때문에 **룸 전체 상태를 하나의 락으로 보호하는 구조는 경합 비용이 커질 수 있다고 판단**했습니다.

대신 룸마다 전용 스레드를 두고, IOCP 워커는 룸 상태 변경 요청을 `JobQueue`에 전달합니다.

```text
IOCP Worker
    │
    ├─ ENTER
    ├─ LEAVE
    └─ BROADCAST
          │
          ▼
      JobQueue
          │
          ▼
      Room Thread
          │
          ▼
      Room State
```

이 구조의 장점은 **룸 상태의 단일 소유권**입니다.

`Room` 내부에는 상태 보호를 위한 별도 mutex가 필요하지 않고, 동일 룸의 작업은 자연스럽게 순서대로 처리됩니다.

`JobQueue::PopAll()`은 큐의 내용을 하나씩 꺼내는 대신 `swap`으로 작업 목록을 가져오기 때문에 락 획득 횟수도 개별 Job 수가 아니라 배치 단위로 줄어듭니다.

다만 이 구조는 **룸 하나의 처리량이 스레드 하나로 제한**된다는 대가를 갖습니다. 실제로 6절에서 이 특성이 측정으로 드러납니다.

## 4. 추가 설계 판단

### RecvBuffer

링 버퍼 대신 **선형 버퍼 + compaction** 방식을 사용했습니다.

패킷 파싱에 연속된 메모리가 필요하기 때문에, 패킷이 버퍼 끝을 넘어가는 상황에서 다시 데이터를 합쳐야 하는 링 버퍼의 복잡성을 피하고 **일반적인 패킷 크기에서는 단순한 선형 구조를 우선**했습니다.

### Session Pool

`SessionData`에 mutex가 포함되어 있기 때문에 `vector<T>` 기반 저장소의 재할당 제약을 피하기 위해 `unique_ptr<T[]>`를 사용했습니다.

고정된 저장소를 사용해 풀에서 꺼내준 객체의 주소가 재할당으로 바뀌지 않도록 했습니다.

### Accept 대기 큐

세션 풀이 고갈된 상태에서도 `AcceptEx` 요청을 버리지 않고 대기 큐에 보관한 뒤, 세션이 반납되면 다시 게시하도록 구성했습니다.

### AcceptEx 주소 파싱

`GetAcceptExSockaddrs`는 런타임에 `WSAIoctl(SIO_GET_EXTENSION_FUNCTION_POINTER, ...)`을 이용해 함수 포인터를 취득하도록 구성했습니다.

## 6. 부하 측정

성능 측정은 최고 수치를 뽑는 것이 아니라 **병목 가설을 세우고 측정으로 검증하거나 기각하는 방식**으로 진행했습니다.

### 측정 환경 — 절을 가로질러 비교하지 않습니다

| | ECHO 스윕 (1~12절) | 룸 / 브로드캐스트 (13절) |
|---|---|---|
| 논리 프로세서 | 20 (i5-13500) | **6** |
| 빌드 | Release x64 · MSVC v143 · C++20 | 동일 |
| 네트워크 | 루프백 | 루프백 |

**머신이 다르므로 절을 가로질러 숫자를 비교하면 안 됩니다.** 아래 표는 전부 13절(논리 프로세서 6개) 기준입니다.

### 측정 결과

| 경로 | 구성 | 결과 |
|---|---|---|
| ECHO | 연결 50 | 왕복 661,169 /초 · p50 0.499 ms |
| Broadcast | 룸 다수 · 팬아웃 약 9 | 유출 약 104,000 /초까지 전달률 100% · p50 1.07 ms |

### 주요 결론 — 서버도 클라이언트도 CPU 바운드가 아니다

논리 20코어에서 다시 측정한 포화 곡선입니다 (연결 100 고정).

| rate | 유출/초 | 전달률 | p50 |
|---:|---:|---:|---:|
| 50 | 100,834 | 100.00% | 0.253 ms |
| 200 | 195,704 | 45.68% | 584.6 ms |
| 400 | 202,331 | 25.34% | 1219.4 ms |
| 800 | 183,729 | 11.76% | 1911.3 ms |

처리량은 약 20만 유출/초에서 평평해지고, 그 위로는 **전달률만 무너지며 지연이 선형으로 증가**합니다.

그런데 그 구간에서도 **서버 CPU는 최대 1.26/20 코어(6.3%), 클라이언트는 0.24/20(1.2%)** 입니다. 어느 쪽도 CPU 바운드가 아니므로 **"서버 한계가 20만"이라고 주장하지 않습니다.** 제약은 연산이 아니라 대기 경로에 있고, 아직 분리하지 못했습니다.

같은 머신에서 루프백을 두 번 통과하는 ECHO가 한 번만 통과하는 브로드캐스트보다 빠릅니다. 두 경로의 유일한 차이는 잡큐를 거쳐 룸 스레드로 넘어가는지 여부이므로, **지연의 원인은 네트워크가 아니라 실행 모델**입니다.

### 재현되지 않은 측정

이전에 **"유출량이 같은데 팬아웃 때문에 지연이 660배 차이난다"** 고 기록했습니다(13절). 같은 비교를 다시 돌렸는데 **논리 20코어에서도, affinity로 6코어에 묶어도 재현되지 않았습니다** — 팬아웃 10과 20에서 p50이 0.24 ms와 0.25 ms로 사실상 같습니다.

머신·툴체인·코드가 동시에 바뀌어 **원인을 분리하지 못했습니다.** 그래서 그 주장은 내리고, 재현 실패를 그대로 [`RESULTS.md` 14절](TestClient/RESULTS.md)에 기록했습니다.

`Room::BroadCast`가 한 스레드에서 동기로 순회한다는 **구조적 사실은 그대로**입니다. 다만 그것이 실제 병목으로 나타나는 조건을 아직 특정하지 못했습니다.

### 기각한 가설

측정 과정에서 세운 병목 가설 중 다음은 측정으로 배제했습니다.

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 전역 SendBuffer 락 | `thread_local` 적용 후 재측정 | 처리량 불변 → 기각 |
| 클라이언트 프로세스 한계 | 부하 클라이언트 2프로세스 분할 | 총량 불변 → 기각 |
| 대역폭 | 패킷 바디 32배 확대 | 왕복/초 불변 → 기각 |

실제 원인은 **부하 클라이언트 자체**였습니다. `GetProcessTimes`로 CPU를 귀속시키자 서버 12.3% / 클라이언트 80.8%로 나왔고, 클라이언트를 논블로킹 + 배칭 구조로 다시 만든 뒤에야 서버의 실제 처리량이 보였습니다.

클라이언트 측 버그를 서버 지연으로 잘못 판단한 경우도 재검증해 제외했습니다.

상세한 측정 과정은 [`TestClient/RESULTS.md`](TestClient/RESULTS.md)에 13개 절로 기록했습니다.

## 8. 현재 상태

### 구현 완료

- IOCP 워커 풀 및 완료 라우팅
- `AcceptEx` 사전 게시 및 재무장
- TCP 패킷 경계 복원
- 비정상 패킷 크기 방어
- 세션 풀 및 참조 계수 기반 수명 관리
- 세션 풀 고갈 시 대기 큐
- 송신 큐 / 송신 직렬화 / 배칭
- SendBuffer 풀 및 공유
- 패킷 핸들러 / 디스패치
- 룸 + JobQueue
- 룸 단위 브로드캐스트
- 세션 종료 시 룸 정리
- CPU 사용량 모니터링
- 종료 시퀀스 — 콘솔 시그널 트리거 · 유입 차단 · 룸 정지 · 세션 정리 · 워커 회수

### 알고 있는 결함

- **부분 전송 미처리** — `transferByte < 요청량`인 경우를 아직 처리하지 않습니다. 루프백·소규모 패킷 환경에서는 관찰되지 않았지만 정합성 구멍입니다.
- **종료 시 게시된 IO를 배수하지 않습니다.** 부하 중 종료 신호를 넣으면 행이나 크래시 없이 내려가지만, **연결 수만큼의 세션이 풀로 반환되지 않습니다** (100 연결에서 100개). 워커를 세우는 시점에 커널에 남아 있던 완료를 꺼내는 주체가 사라져 참조가 풀리지 않기 때문입니다. 측정값과 원인은 [`RESULTS.md` 14절](TestClient/RESULTS.md)에 있습니다.
- 종료 경로의 `Recv Error` 로그는 실제 오류가 아니라 정상 teardown입니다. 억제가 필요합니다.
- 세션 종료 경로가 나뉘어 있어 일원화가 필요합니다.
- `Job_Leave` 중복 게시 방지가 없습니다.

### 개선 예정

- 종료 4단계(드레인) — 세션 풀이 다 찰 때까지 대기 + 타임아웃
- `CTRL_CLOSE_EVENT`(창 닫기) 처리 — 핸들러가 종료 완료까지 대기하는 구조 필요
- 로깅 시스템 도입
- 설정값 하드코딩 제거 (포트, 풀 크기)
- 룸 배정 정책 개선 (현재 무작위 배정)
- 싱글톤 의존성 정리
- 테스트 프로젝트 빌드 자동화

### 의도적으로 범위에서 제외

DB · 인증 · 재접속 · 프로토콜 버저닝은 다루지 않았습니다. 이 저장소는 **네트워크 계층과 룸 처리 구조를 검증하는 데 집중한 프로젝트**입니다.

   /I jhshin_Server ^
   TestClient\LoadTestRoom.cpp ^
   /Fe:LoadTestRoom.exe ws2_32.lib
